# 睡眠延迟变化与删除队列

## 当前执行流程

先生成并保存完整备份及固定计划。在手机现有原版的睡眠所有数据页，仅删除计划所选整晚，完成正常同步，然后勾选面板的手机删除确认。单日CLI同时要求`--allow-sleep-delete --phone-night-deleted`；批量CLI同时要求`--allow-sleep-delete --phone-nights-deleted`。

程序核验所选睡眠查询窗的云分段和当日日汇总均为空，运动基线仍与计划一致，再清理电脑旧睡眠。原版本地删除可能仅设置`sync_status=2`，所以不能以删除函数返回true判定数据库已清空。程序读回核心分段、睡眠字典及统计的待删除项；只有再次确认云端删除完成后，才在限定范围事务中物理清除已完成的本地删除任务和该晚旧入睡／起床字典字段。旧字典可能因原版严格比较结束时间而保留已同步状态，不能只检查它的待删除状态。未归零便停止，不上传新分段。

重建按批上传并读回，随后检查完整旧／新查询窗及日汇总，识别目标末尾之外的旧尾段。短期核验通过仍需手机正常同步与后续手表同步验收。

批量睡眠也需要先清理手机所选各晚。所有日期云分段／汇总为空且运动基线一致，才开始第一天写入；每一天再核验。已经成功的日期不会自动回滚，任何失败都停止后续日期。不要在删除手机记录之后重新从空数据生成睡眠计划，应使用删除前保存的完整计划。

## 原流程的错误

原流程自动清电脑并删云后立即重建，有三个缺口：本地查询过滤了待删除记录；删除请求按时间和睡眠类型匹配，未绑定阶段或新记录版本，延迟执行可以删到同时间的新分段；电脑清理不清手机本地旧记录，普通增量下载也不保证移除云端缺失的本地段。云分段正确而日汇总变长，应分开诊断。

原guard仅挂健康后台，主进程也能访问相同数据库和账号。在故障诊断启动期间观察到非预期后台删除，故不能将该次诊断称作完全只读无副作用。修复后同时挂当前主进程和后台，关闭ART优化以避免已编译调用绕开Hook，新增进程保持暂停并停止任务。未知厂商实现变化仍需重新定位，不能承诺覆盖任何接口。

## 电脑隔离与证据

每个会话先断开电脑应用网络，确认所有当前应用进程guard就绪和新增进程门槛后才联网。退出先停止应用、安装并核验该应用UID的IPv4/IPv6隔离，再detach并撤临时规则。隔离安装失败保留临时阻断和会话锁。隔离仅影响研究电脑，手机正常使用不受影响。

`health_panel_quarantine`在当前模拟器运行期间保留，普通重新打开电脑应用仍离线；它不是手机规则，也不是跨模拟器重启的防火墙配置。问题修复前勿自行重启模拟器后启动同步。面板受控会话会重新安装规则；最终必须清掉电脑旧源，不能只依赖隔离。

证据包含`session_guard_private.json`、本地删除读回、已完成删除队列清理响应、完整窗口重复核验及最终guard状态。旧任务和所有started标记保留。恢复任务必须独立创建并注明完整备份来源，不能用残缺云数据整体平移或删除旧标记重跑。

从完整备份恢复与合成新分段不同。原评分恢复只是复制原值；不保留评分的原请求仍按原规则提交0。手机最终显示、云核验和长期稳定性分别记录。
